# 项目三：竞品 / 店铺评价洞察 —— 需求文档（PRD）

> 定位：个人练手项目，模拟「AI 产品 / 运营」用评价数据做复盘、反哺运营决策。
> 目标：把零散差评变成**可执行的改进清单**，而不是只看平均分。

## 1. 背景与痛点

- 店铺评价散、量大，人工看不过来，往往只看星级。
- 差评原因混杂（质量/物流/尺寸/色差/服务），没有归因就改不动。
- 改完也不知道优先改哪个，资源错配。

## 2. 目标用户与场景

- 中小电商运营/店主做周度复盘；本项目以「包包」示例评价数据演示。
- 场景：导入评价 → 情感分布 → 差评归因 → 改进建议 → 给负责人_summary。

## 3. 功能需求（FR）

| 编号 | 功能 | 说明 | 优先级 |
|------|------|------|--------|
| FR1 | 数据导入 | 粘贴评价或载入示例 CSV | P0 |
| FR2 | 情感分类 | 正/中/负 三分类（规则或模型） | P0 |
| FR3 | 差评归因 | 命中 质量/物流/尺寸/色差/服务 类别 | P0 |
| FR4 | 改进建议 | 归因 → 映射运营可落地的动作 | P0 |
| FR5 | 自然语言总结 | 接 key 后大模型生成给负责人的总结 | P1 |
| FR6 | 演示模式 | 无 key 用规则分析，流程可演示 | P1 |

## 4. 非功能需求（NFR）

- 单次分析 < 3s（规则版瞬时；模型版按调用计）。
- 归因关键词、改进映射可配置、可换类目。

## 5. 关键设计决策（面试可讲）

- **为什么先规则再模型？** 归因是确定性业务标签，规则可解释、可审计、零成本；模型适合做"总结"这类开放任务，分工清晰。
- **为什么输出"改进清单"而不是"情感分"？** 运营要的是动作，情感分只是诊断，归因+建议才是闭环。
- **类目适配**：CATEGORIES 与 IMPROVE 两张表换一下就能从包包切到服饰/3C，体现可复用设计。

## 6. 验收标准

- [ ] 能导入示例数据并分类情感
- [ ] 差评能归到正确类别并计数
- [ ] 能输出按类别映射的改进建议
- [ ] 不填 key 可进入演示模式

## 7. 边界与风险（诚实说明）

- 规则归因靠关键词，长难句/反讽会误判（如"质量好得没话说"含"质量"但正向），真实落地需模型或人工抽检。
- 示例数据为合成样本，不代表真实业务表现。
- 大模型总结仅辅助，最终决策由人做。
