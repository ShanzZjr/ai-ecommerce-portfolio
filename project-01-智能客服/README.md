# 项目一：电商智能客服原型 —— 需求文档（PRD）

> 定位：个人练手项目，模拟「AI 产品 / 运营」在真实店铺里落地一个客服 Agent 的全过程。
> 目的不是把代码写多牛，而是展示**怎么把业务痛点翻译成可落地的 AI 功能，并守住风险边界**。

## 1. 背景与痛点

- 一人店铺售前咨询高度重复：尺寸、材质、色差、发货、退换占咨询量 70%+，店主重复手打。
- 夜间 / 大促爆量时无人响应，流失转化。
- 新手客服（或 AI）容易**乱承诺发货时间、赠品、赔付**，引发投诉与平台纠纷。

## 2. 目标用户与场景

- 用户：中小电商卖家（本项目以「包包店」为示例）。
- 场景：售前高频问答自动应答、夜间值守、低风险问题兜底。

## 3. 功能需求（FR）

| 编号 | 功能 | 说明 | 优先级 |
|------|------|------|--------|
| FR1 | 知识库检索 | 把店铺 FAQ 结构化，按用户问法检索最相关条目 | P0 |
| FR2 | 大模型问答 | 仅基于命中知识生成自然回复，禁止编造参数 | P0 |
| FR3 | 转人工规则 | 命中退款/订单/投诉/议价/定制/赔付等，强制转人工 | P0 |
| FR4 | 配置面板 | 可选模型、填 key，key 仅存会话内存不落盘 | P1 |
| FR5 | 演示模式 | 无 key 时用规则命中返回示例答案，证明流程闭环 | P1 |

## 4. 非功能需求（NFR）

- 响应延迟 < 3s（单次大模型调用）。
- 知识库可一键替换（结构固定，内容可改）。
- 零部署：本地 Flask 网页，店主自己能跑。

## 5. 关键设计决策（面试可讲）

- **为什么不直接让大模型自由答？** 电商客服答错参数 = 承诺 = 纠纷。所以用「检索 + 约束提示词」把模型锁在知识范围内。
- **转人工为什么用「规则 + 关键词」双保险？** 模型偶尔不乖，关键词触发（退款/订单等）强制拦截，保证钱和承诺类绝不交给 AI 乱说。
- **演示模式的价值**：证明「即使没接 API，流程也闭环」，也方便面试官无 key 直接看。

## 6. 验收标准

- [ ] 输入标准问题能命中知识并给出自然回复
- [ ] 输入退款/订单等敏感词，输出为转人工话术，无具体承诺
- [ ] 输入知识库外问题，转人工而非瞎编
- [ ] 不填 key 可进入演示模式，页面正常

## 7. 边界与风险（诚实说明）

- 这是原型，未接真实订单/物流系统，转人工目前是「提示」，真实落地需对接工单。
- 大模型回复仍需人工抽检，不能 100% 免责。
- 知识库质量决定上限，需持续运营更新。
